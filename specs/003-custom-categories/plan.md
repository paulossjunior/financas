# Implementation Plan: Categorias Personalizadas de Despesas

**Branch**: `003-custom-categories` | **Date**: 2026-06-08 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from [specs/003-custom-categories/spec.md](spec.md)

---

## Summary

Adds user-managed expense categories with keyword-based auto-classification rules, automatic reprocessing of in-memory invoices when rules change, and manual transaction category overrides with cross-session persistence. The Rust backend is ~80% ready — `CategoryRule`, `AppConfig.category_rules`, `Categorizer::new()`, and `save_config`/`get_config` all exist. New backend work: one `AppConfig` field, two domain changes (deterministic Invoice ID, transaction override application), and three new Tauri commands. All frontend work is new: a Settings page category management UI and (P3) transaction override UI in Dashboard.

---

## Technical Context

**Language/Version**: Rust 1.75 (Tauri backend) + TypeScript 5 / Vue 3 (frontend)

**Primary Dependencies**:
- Backend: `uuid` crate (already present — use `Uuid::new_v5` for deterministic IDs), `serde` + `serde_json` (already present — add `#[serde(default)]` on new field)
- Frontend: Pinia, `@tauri-apps/api/core` `invoke`, existing `tauri.service.ts` pattern

**Storage**: `config.json` in app config dir (via existing `ConfigStore`). `InvoiceStore` remains in-memory.

**Testing**: `cargo test` (Rust unit), `npm run test` (Vitest unit), `npx playwright test` (E2E)

**Target Platform**: macOS desktop (Tauri v2)

**Project Type**: Desktop app — Tauri v2 (Rust backend + Vue 3 frontend)

**Performance Goals**: Recategorization of a full session's invoices (typical: 3–12 invoices, 300–2000 transactions) < 200ms.

**Constraints**: All data local-only. No network calls. `InvoiceStore` in-memory only — no XLSX reimport on rule change.

**Scale/Scope**: Single user, single machine. Up to 50 categories, 500 keyword rules, 10 000 transactions per session.

## Constitution Check

### Principle I — TDD (Non-Negotiable)

- **PASS**: All implementation tasks must be preceded by failing tests. Rust domain changes (`Invoice::new_v5`, `recategorize_invoices`) get unit tests first. Frontend components get Vitest tests first. E2E scenarios in `tests/categories.spec.ts` are written before UI implementation.

### Principle II — Clean Architecture

- **PASS**: New Rust commands follow the existing layer pattern: `commands/` → `application/` → `domain/`. `recategorize_invoices` lives in `application/` as a use case. `Invoice::id` change stays in `domain/`. TypeScript service functions in `tauri.service.ts` keep frontend/backend separation.

### Principle III — YAGNI / Simplicity

- **PASS**: No new `Category` entity struct — categories are implicit in `Vec<CategoryRule>`. No new `CategoryStore` — reuses `ConfigStore`. Frontend `CategoryGroup` is a pure computed view-model, not persisted.

### Principle IV — Data Integrity

- **PASS**: `transaction_overrides` field uses `#[serde(default)]` so existing `config.json` files parse cleanly. Deterministic Invoice ID via `Uuid::new_v5` is a forward-compatible change (in-memory store, no migration needed). `override_transaction_category` validates non-empty category before persisting.

### Principle V — Local-First & Privacy

- **PASS**: All three new commands operate on local state only. No network calls. `config.json` remains on-device.

## Implementation Phases

### Phase 0 — Backend Foundation (blocks all stories)

Changes to Rust core. All must be TDD (tests first, must fail, then implement).

1. **`domain/invoice.rs`**: Change `Invoice::new()` to use `Uuid::new_v5(Uuid::NAMESPACE_URL, filename.as_bytes())`. Unit test: same filename always produces same `Invoice.id`.

2. **`domain/mod.rs`**: Add `transaction_overrides: HashMap<String, String>` to `AppConfig` with `#[serde(default)]`. Unit test: deserialization of old config (without the field) produces empty map.

3. **`application/import_invoice.rs`**: After categorization, apply overrides: `if let Some(cat) = config.transaction_overrides.get(&tx.id.to_string()) { tx.category = cat.clone(); }`. Unit test: override applied correctly after import.

4. **`application/recategorize.rs`**: New use case `recategorize_invoices(store, config) -> usize`. Iterates all invoices, recategorizes, applies overrides, returns change count. Unit test: verify count, verify override applied, verify "Outros" fallback.

5. **`commands/categories.rs`**: Three new Tauri commands (`recategorize_invoices`, `override_transaction_category`, `remove_transaction_override`). Integration test via Rust test or Playwright mock.

6. **`lib.rs`**: Register new commands in Tauri builder.

### Phase 1 — US1: Gerenciar Categorias (P1 — MVP)

Frontend Settings page with category management.

**Goal**: User can create, rename, delete categories. Changes persist to `config.json`.

1. **`src/types/api.types.ts`**: Add `transaction_overrides` to `AppConfig`; add `CategoryGroup` interface.

2. **`src/services/tauri.service.ts`**: Add `recategorizeInvoices()` service function.

3. **`src/__tests__/stores/settings.store.test.ts`** (TDD — write first, must fail):
   - `categoryGroups computed correctly from category_rules`
   - `addCategory adds new CategoryGroup`
   - `deleteCategory removes all rules for that category`
   - `renameCategory updates category string in all matching rules`
   - `saveCategories calls save_config then recategorize_invoices`

4. **`src/stores/settings.store.ts`**: New Pinia store. State: `config: ref<AppConfig>`. Computed: `categoryGroups: CategoryGroup[]` (group rules by category name). Actions: `loadConfig`, `addCategory`, `deleteCategory`, `renameCategory`, `saveCategories`.

5. **`src/components/settings/CategoryList.vue`**: List of categories, add button, delete/rename per row.

6. **`src/pages/SettingsPage.vue`**: Add "Categorias & Regras" section using `CategoryList.vue`. On mount: initialize `settings.store` if not already loaded. On save: call `settings.store.saveCategories()`.

7. **`tests/categories.spec.ts`** (Playwright — US1 scenarios): Mock `get_config`, `save_config`, `recategorize_invoices`. Test create/rename/delete flows.

### Phase 2 — US2: Regras de Categorização (P2)

Keyword management within each category.

**Goal**: User can add and remove keywords per category. Conflict detection. After save, rules applied to in-memory invoices.

1. **`src/__tests__/utils/category-conflict.test.ts`** (TDD — write first): `detectConflict(keyword, categoryName, groups) → { conflict: boolean, existingCategory: string | null }`.

2. **`src/utils/category-conflict.ts`**: Implement conflict detection utility.

3. **`src/components/settings/CategoryGroupEditor.vue`**: Inline editor: keyword chip list, add keyword input with conflict warning, priority input. Emits `save`, `delete`.

4. Update `CategoryList.vue` to use `CategoryGroupEditor`.

5. Add US2 Playwright scenarios to `tests/categories.spec.ts`: add keyword → import mock fatura → verify categorization.

### Phase 3 — US3: Reclassificação Manual (P3)

**Goal**: User selects a transaction's category manually. Override persists across sessions. User can remove override.

## Complexity Tracking

| Violation | Why Needed | Simpler Alternative Rejected Because |
|-----------|------------|-------------------------------------|
| Changing `Invoice::id` generation | US3 override persistence requires stable transaction IDs across sessions | Alternative key strategies (`filename+row_index`) require threading filename through every transaction lookup — more invasive than changing one line in `Invoice::new()` |

## Key Design Decisions Summary

See [research.md](research.md) for full rationale. Summary:

| Decision | Choice |
|----------|--------|
| Category entity | Implicit — `category` string in `CategoryRule`, no separate struct |
| Reprocess trigger | New `recategorize_invoices` Tauri command, called after `save_config` |
| Transaction ID stability | `Uuid::new_v5(NAMESPACE_URL, filename)` for `Invoice::id` |
| Override persistence | `HashMap<String, String>` in `AppConfig`, persisted in `config.json` |
| Conflict detection | Client-side, before save, inline warning (non-blocking) |
| Default rules UX | Pre-populate Settings UI with defaults when `category_rules` is empty |
| US3 access point | Dashboard category transaction rows (expand existing card) |
